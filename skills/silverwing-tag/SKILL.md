# Silverwing 测试 Tag

## 预检与确认

1. 用 `sw tag list --task "<任务目录名>"` 查找指定服务和模块，取中文输出中的「服务选择值」。
2. 用 `sw tag build --task "<任务目录名>" --service "<服务选择值>" --dry-run` 预检。多服务重复 `--service`，用户要求全部时用 `--all-services`。记录「预检编号」。遇到冲突，按下节解决并暂存，再用相同参数加 `--preflight "<预检编号>"` 复检。CLI 报告基线变化时重新预检。
3. CLI 显示「预检全部通过」后，展示服务、分支和预估 Tag。多个构建项共用 Genbu 服务时，先确认分批或各项的部署范围。当前任务未获全自动授权时，提供以下选项，收到用户明确选择后再继续。

   - **本批全自动（默认）**。执行本批构建、通知测试负责人、等待 UAT 发版完成并执行自测和观测。下一个批次重新选择。
   - **本任务全自动**。执行本批，当前 Silverwing 任务后续批次也在预检全部通过后自动执行全流程。切换任务时重新选择。
   - **停止，等待用户观测**。停在预检结果，交给用户观测，等待下一步指示。

## 执行与跟进

### 构建与冲突

- 获得确认后保留服务选择和 `--preflight "<预检编号>"`，去掉 `--dry-run` 执行。记录批次 ID、操作 ID 和实际 Tag。预检编号已使用时查询同一批次。
- 在 CLI 给出的「冲突工作区」内处理「冲突文件」。以目标 B 为基线，将 A 合并到 B。禁止将 B 分支合并到 A 分支。
- 用 `git diff --cc` 对照冲突。`git show :2:<路径>` 查看目标 B，`git show :3:<路径>` 查看源 A。业务取舍不明确时展示差异，请用户判断。
- 暂存已核对的文件并运行相关检查。预检阶段复检原编号。批次执行后失败或中断时，用 `sw tag status --batch "<ID>"` 查看原操作，再用 `sw tag retry --operation "<ID>"` 续接。先处理「阻塞操作 ID」，基线变化时保留现场并报告。

### 通知、发版与自测

Genbu 编译、UAT 发版、Pod 和运行版本使用 `genbu-cli` 命令行核实，批次信息由 `sw tag status` 汇总。不使用 Computer Use、浏览器或网页截图确认这些状态。

1. 用 `sw tag status --batch "<ID>"` 查询逐服务的 Tag 推送、Genbu 编译和 UAT 发版。等待期间每 30 秒查一次，最多 20 分钟。编译失败时用 `genbu-cli` 按输出的「Genbu 服务」和 Tag 查日志。
2. CLI 显示「整批 Tag 已推送且编译成功」后，用 `sw tag notify --batch "<ID>"` 以当前 Lark 用户身份私聊通知需求的测试负责人。CLI 负责登录验证、联系人匹配及去重；不改用机器人。报告实际接收人和逐人回执，部分失败或结果待核实时用原批次重试，已成功的人不会重复发送。如果 CLI 因需求或联系人无法确定而回退本人，明确提醒用户自行转发给测试负责人。登录或权限不足时按 CLI 提示补齐后续接。
3. 通知后继续等待并监控同一批次。普通批次确认「整批 UAT 发版成功」及「目标版本已就绪，可以自测」。同一 Genbu 服务使用不同 Tag，或已分别确认部署范围时，用 `sw tag status --operation "<ID>" --namespace "<名称>"` 逐项确认各范围内每个操作的 Tag 推送均为「已推送且提交一致」，Genbu 编译和 UAT 发版均为「成功」，且显示「UAT 运行状态 目标版本已就绪」。全部已确认的目标范围通过后，继续第 4 步自测。部署范围不明或运行版本被覆盖时，先汇报并确认范围。失败或超时时报告各服务最新状态和证据。
4. 目标版本就绪后，主动执行任务约定的 UAT 自测并观测日志、接口响应和关键业务结果，报告实际用例及结果。自测依赖缺失时说明具体阻断和已完成项；发现本次改动的问题时修复，并按已有授权重新预检、构建和验证。
