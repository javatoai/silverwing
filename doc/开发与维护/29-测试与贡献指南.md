## 从改动范围选择验证

仓库的测试以 Go 包内 `*_test.go` 为主。改动配置校验或持久化时，优先运行 `go test ./internal/domain ./internal/storage`；改动任务、Git 或工作区流程时，运行 `go test ./internal/workspace ./internal/application`；改动页面状态或交互逻辑时，运行 `go test ./internal/desktop ./internal/application`。这些命令从仓库根目录执行，只测试列出的产品模块，适合作为快速反馈。

以下示例以 Go 1.27.1、Windows PowerShell 和仓库根目录为前提；在其他开发系统可从仓库根目录运行相同的 Go 参数。Go 会按当前宿主系统自动选择平台文件。

```powershell
go test ./internal/domain ./internal/storage
go test ./internal/workspace ./internal/application
go test ./internal/desktop ./internal/application
```

跨多个模块的修改再运行根模块完整检查 `go test ./...`。Go 会自动选择当前宿主系统适用的文件和测试：例如 Windows 专属用例带 `//go:build windows`，其他系统不会执行这些用例。因此，在 Windows 上通过不能代替 macOS 上针对菜单、文件系统、剪贴板或原生渲染行为的检查；更改平台适配时，应在目标系统进行人工启动与操作。

## MyGO 补丁需要单独测试

`third_party/mygo` 有自己的 `go.mod`，是独立 Go 模块。根目录执行 `go test ./...` 不会进入这个嵌套模块；如果修改 MyGO 本地补丁，应切换到模块目录再验证：

```powershell
Push-Location third_party/mygo
go test ./...
Pop-Location
```

发行构建使用 `mygo_noinspector` build tag 编译 Silverwing，跳过 MyGO 的可选内容检查器。需要确认与发行一致的编译变体时，可追加检查：

```powershell
go test -tags mygo_noinspector ./cmd/silverwing ./internal/desktop
```

这个命令以 `mygo_noinspector` 选择依赖源码，编译并运行列出的 Silverwing 根模块包测试；它不会运行 MyGO 依赖模块自己的 `*_test.go`。MyGO 自身测试仍需在 `third_party/mygo` 内另行运行，并明确是否使用 `go test -tags mygo_noinspector ./...`；发行 tag 的检查也不能取代默认 tag 的验证。

MyGO 的键盘、菜单、IME、剪贴板和绘制补丁还可能依赖原生窗口系统；包测试通过只能证明覆盖到的代码，不代表每个平台的界面体验都已验收。补丁入口和升级注意事项见 `third_party/MYGO-PATCHES.md`。

## 单元测试以外的检查

涉及外部 CLI、环境变量、代理、账号隔离、读写权限或进程取消时，使用专用测试账号和虚构仓库逐项验证：程序能否找到预期命令，错误输出是否可诊断，取消后子进程是否结束，以及失败操作有没有留下部分状态。不要拿真实任务资料或生产 CLI 登录状态当测试夹具；路径隔离方法见[本地开发与调试](28-本地开发与调试.md)。

界面修改至少在目标操作系统启动相关页面，检查正常窗口尺寸、主题、键盘和鼠标操作；截图可以附在 PR 里帮助审阅，但不能替代交互验证。原生媒体、安装包和 CLI 依赖检查应按变更风险选择，不需要每个文案改动都构建全平台发行包。

## CI 和 PR

当前 `.github/workflows/native-build.yml` 会在分支推送、PR、手动触发和 `v*` 标签推送时检查产品版本并构建 Windows x64、macOS arm64 包；普通构建产物保留 14 天。该 workflow 没有 Go 测试步骤，所以 PR 的绿色构建不代表单元测试已经运行。修改代码时应在本地补上与改动匹配的测试，并在 PR 描述中列出实际执行的命令和结果；改了 UI 时可附关键界面的截图。

仓库现有贡献入口以正常 PR 审阅和工作流为准，没有额外强制的 PR 清单或提交格式要求。提交前查看自己的差异，避免夹带无关本地文件；保持讨论聚焦于变更目标、验证范围和已知限制即可。

## 源码入口
