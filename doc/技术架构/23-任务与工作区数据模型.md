# 任务与工作区数据模型

[← 知识库目录](../Index.md)

本文说明 Go / MyGO 版 Silverwing 当前保存的任务与工作区关系。核对日期：2026-10-19；任务清单 schema 为 `2.0.0`。

![任务、模块与工作区之间的数据关系示意](../assets/workspace-model.png)

## 配置如何变成任务

配置保存可复用的仓库和服务关系：一个 `GroupConfig` 包含多个 `GroupServiceConfig`；服务指向一个 `RepositoryConfig`，并带有一个或多个 `ServiceModuleConfig`。模块各自保存工作区策略、主分支、Tag 设置等。创建任务时，用户选择组、服务和模块，应用再按每个选中的模块准备一个工作区。

任务实例保存在 `TaskManifest`。它有一个 `services` 数组，其中每个元素是 `ServiceWorkspace`，因此任务和工作区是一对多：例如两个服务各选两个模块，清单里会有四条工作区记录。同一仓库也可能对应多条记录，不能只用仓库路径或服务名称区分。

工作区的业务身份由 `groupServiceId + moduleId` 组成，桌面投影的 ID 使用 `服务ID:模块ID`。`repositoryId` 标识 Git 仓库，`worktreePath` 标识具体工作目录；这些字段职责不同。配置中的 `moduleId` 与名称也不是目录身份，目录名由创建流程生成并做冲突检查。

## 路径与身份

任务根目录来自当前配置。任务目录必须是任务根的直接子目录，创建流程把每个模块工作区放在任务目录下的独立子目录。标准 Git Worktree 连接到原仓库的 Git 元数据；独立克隆则有自己的克隆目录。清单分别记录 `repositoryPath` 和 `worktreePath`，不要从一种策略推算另一种路径。

清单没有单独的 UUID `taskId` 字段。应用以任务目录名作为任务 ID，并校验它等于清单的 `taskDirectoryName`。`folderName` 是展示名称，`createdAt` 和组、分支等字段会被敏感操作用来再次确认任务身份。相同目录名放在不同任务根下，不代表同一个任务。需求资料目录由 `requirementMaterials.writeRoot` 单独记录，可以位于任务根之外。

## 清单结构与状态

下面只展示关系所需字段。路径、名称和时间都是虚构值；片段省略了多个实际字段，**不是完整 manifest，也不可直接导入**。

```json
{
  "schemaVersion": "2.0.0",
  "folderName": "支付渠道优化",
  "taskDirectoryName": "支付渠道优化",
  "featureBranch": "feature/payment-channel",
  "createdAt": "2026-10-19T09:00:00Z",
  "updatedAt": "2026-10-19T09:00:00Z",
  "lifecycleStatus": "ACTIVE",
  "groupId": "default",
  "services": [
    {
      "repositoryId": "repo-web",
      "groupServiceId": "service-web",
      "moduleId": "frontend",
      "repositoryPath": "D:/work/web",
      "worktreePath": "D:/tasks/支付渠道优化/web-frontend",
      "branch": "feature/payment-channel",
      "strategy": "STANDARD_WORKTREE",
      "health": "READY"
    },
    {
      "repositoryId": "repo-api",
      "groupServiceId": "service-api",
      "moduleId": "gateway",
      "repositoryPath": "D:/work/api",
      "worktreePath": "D:/tasks/支付渠道优化/api-gateway",
      "branch": "feature/payment-channel",
      "strategy": "INDEPENDENT_CLONE",
      "health": "READY_WITH_WARNINGS"
    }
  ]
}
```

`lifecycleStatus` 只表示任务处于 `ACTIVE` 或 `ARCHIVED`。工作区 `health` 记录创建及初始化结果：`CREATING`、`READY`、`READY_WITH_WARNINGS` 或 `FAILED`。任务聚合健康状态时按失败、创建中、有警告、就绪的优先级计算；它不代表 Git 当前是否干净。

Git 检查是另一组运行时结果，包含检查状态、实际与预期分支、脏文件数、未推送提交数和问题类型。目录缺失、分支不匹配、detached HEAD 或 Git 操作进行中，都可能在清单仍为 `READY` 时出现。排查时分别看“工作区健康”和最新 Git 状态。

## 读取、保存与生命周期

当前 `ManifestStore` 只接受当前 schema 版本。读取会拒绝无效 UTF-8、缺失或不支持的版本、字段类型错误和严格解码失败；扫描任务根时只检查直接子目录，并把不支持的版本与损坏清单分开报告，不会自动覆盖它们。保存会规范化列表字段，先写同目录临时文件并同步，再替换正式清单。

归档和恢复更新清单中的生命周期状态，不等于删除或重建工作区。永久删除会按清单记录核对并清理任务目录及所拥有的工作区；位于任务目录外的需求资料根不由任务目录枚举负责清理。手工改动路径或身份字段会触发安全校验，先通过应用的修复、恢复或迁移流程处理。

## 源码入口

- 数据结构、枚举与默认值：`internal/domain/models.go`
- schema 校验与健康状态聚合：`internal/domain/validation.go`
- 任务与工作区 DTO 投影：`internal/application/app.go`、`internal/application/contracts.go`
- 创建工作区与目录冲突检查：`internal/workspace/task_application.go`、`internal/workspace/provisioner.go`
- 清单读写与扫描：`internal/storage/manifest_store.go`
- 删除时的路径与所有权校验：`internal/workspace/lifecycle.go`
- 动态 Git 健康模型：`internal/domain/workspace_git_health.go`
