01 / WHY SILVERWING

当需求跨越仓库，
上下文就应该跟着走。

传统方式需要你在多个目录、分支、终端和说明文件之间来回切换。silverwing 把这些零散动作收束成一个任务现场，让“开始开发”本身变成一件可复用的事情。

01
⌁

一项需求，多个工作区

选择本次要修改的服务，silverwing 为每个服务准备独立 Worktree 或独立克隆。主 checkout 不被切换，多个任务可以并行存在。

task→api+web+gateway
02
✦

说明文件，不再漂移

全局、组、任务三级 AGENTS.md 合成在一起。系统区可重新生成，人工区被保留，外部编辑还能感知冲突。

GLOBALGROUPTASK
03
⌘

Git 状态，一眼可见

未提交、未跟踪、未推送、分支异常和工作区缺失，都在任务详情中直接显现。状态检查只读，不偷偷 Fetch。

本地健康度
04
↗

交付动作，有边界也有历史

Tag 构建前先做风险检查和合并预检，构建结果与历史记录保存在任务目录里。你可以清楚知道发生了什么，也始终保留最后的决定权。

delivery.log
$ silverwing tag build --task 7060612727
checking workspace health...
✓ no uncommitted changes
✓ upstream is reachable locally
→ tag: release/test-1.2.58
02 / THE WORKFLOW

从配置到交付，
每一步都留在任务里。

silverwing 不试图接管你的开发工具，而是把它们放进同一个清晰的上下文中。你继续使用 IDEA、WebStorm、Codex 或 Cursor，silverwing 负责把现场准备好。

05 / SAFETY BY DEFAULT

安全不是一个开关，
而是每个动作前的习惯。

silverwing 的价值不只是帮你创建目录，而是把“不要误伤现有工作”落实到工作区生命周期的每个关键节点。

⌁
不切换主 checkout

标准 Worktree 从远程引用创建，不移动你正在使用的主目录。

✓
◉
不偷偷联网刷新状态

日常状态只比较本地已知 upstream；Fetch 由明确的创建动作触发。

✓
↯
不 Force Push / 不自动 Rebase

冲突、推送与合并仍由你决定，系统不会替你跨过风险边界。

✓
▣
归档和删除前先检查

未提交、未推送、进行中的 Git 操作都会在动作前显式暴露。

✓
“

自动化应该减少重复劳动，
而不是减少人的判断。

”
